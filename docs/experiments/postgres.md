# Experiment: PostgreSQL instead of CockroachDB

This is an experiment on the branch `exp/postgres-tests`.
It never merges, and it touches no production data.
The question is how much faster the backend's database tests get on PostgreSQL, and what a real move takes.

Status: Phase 1 is measured in a VM.
The CI timing (Phase 2) is filled in from the draft PR's runs; its rows say "pending" until then.

## What ran

| Item                 | Value                                                                                                       |
| -------------------- | ----------------------------------------------------------------------------------------------------------- |

## Every incompatibility

Every migration after the first failure cascades; the rows below are the root causes.
All 288 migrations apply on PostgreSQL once these are handled.

| Where                                                                                 | Error on PostgreSQL                                  | Smallest change that runs on both                                                                                                      | Safe on production's CockroachDB?                                                                                                             |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 00004, 00005, 00011, 00020, 00035, 00122, 00179, 00203 (two statements), 00223, 00286 | `unrecognized parameter "ttl_expiration_expression"` | None in SQL. The experiment cuts the clause from the text goose reads (`migrations/postgres.go`). A real move removes TTL (see below). | Only as a PostgreSQL-only shim. Editing the applied files would drop TTL on a fresh CockroachDB.                                              |
| 00168 `kind STRING`                                                                   | `type "string" does not exist`                       | `TEXT`                                                                                                                                 | Yes. `STRING` is an alias of `TEXT`; only the file's hash changes.                                                                            |
| `migrations/lock.go` `holder STRING`                                                  | same                                                 | `TEXT`                                                                                                                                 | Yes, same reason.                                                                                                                             |
| 00221 `seq INT8 DEFAULT unique_rowid()`                                               | `function unique_rowid() does not exist`             | Experiment: a prelude defines `unique_rowid()` over a sequence. A real move: `GENERATED BY DEFAULT AS IDENTITY` in a new migration.    | The prelude only runs on PostgreSQL. The identity column also works on CockroachDB, but changes applied history, so it needs a new migration. |
| `play/combat_fog.go` `$2::STRING`                                                     | `type "string" does not exist`                       | `$2::TEXT`                                                                                                                             | Yes. | dbtest: `SHOW CREATE TABLE/SEQUENCE/FUNCTION/TRIGGER`                                 | syntax error                                         | Not needed with `CREATE DATABASE … TEMPLATE`; the dump variant uses `pg_dump --schema-only`.                                           | Not applicable.                                                                                                                               |
| dbtest: `INSERT … SELECT * FROM <template>.public.<table>`                            | cross-database queries do not exist                  | Native template copy, or `COPY` out and in.                                                                                            | Not applicable.                                                                                                                               |

Row-level TTL is set on 7 tables, by 10 migration statements (the brief said 10 tables).

| Table               | Expression                                                                                         |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| `auth_sessions`     | `expires_at`                                                                                       |
| `oidc_login_states` | `expires_at`, job hourly                                                                           |
| `campaign_invites`  | `expires_at + 30 days`                                                                             |
| `campaign_members`  | `pending_expires_at`                                                                               |
| `characters`        | `CASE WHEN kind = 'player' AND player_user_id IS NULL AND campaign_id IS NULL THEN created_at END` |
| `claim_links`       | `COALESCE(used_at, revoked_at, expires_at) + 30 days`                                              |
| `claim_sign_ins`    | `expires_at`                                                                                       |

On PostgreSQL each expression becomes a sweep handler on the existing Cloud Tasks path: `DELETE … WHERE <expression> < now()` in batches, with an index on the expression.
Reads must already ignore expired rows, as `TestQ24_PendingMemberPastTheDeadlineIsNoMemberBeforeTheTTLJobRuns` requires on CockroachDB.

## Failures by class

About 300 tests ran on PostgreSQL, picked for transactions, the 40001 retry, TTL, unique and foreign-key errors, ordering, JSON and time.
They were selected by name, never whole packages.
All of those not listed below passed.
No row-order, error-text or `INT`-width difference showed in that sample.

## Timings in the VM

The commands:

```
MEURPG_EXPERIMENT_TIMING=1 MEURPG_TEST_DATABASE_URL=<url> go test ./internal/platform/dbtest -run TestExperimentTimings -v -count=1
RE='^(TestRN|TestQ|TestMR|TestSignIn|TestUpdateCampaign|TestXp)'   # 41 tests
MEURPG_REQUIRE_DB=1 MEURPG_TEST_DATABASE_URL=<url> flock /tmp/meurpg-test.lock go test -race -count=1 -run "$RE" ./internal/campaigns
```

| Step                                                             | CockroachDB | PostgreSQL                                 |
| ---------------------------------------------------------------- | ----------- | ------------------------------------------ |
| One fresh migrate of all 288 migrations                          | 112 s       | 0.5 s                                      |
| Drop that database                                               | 7.1 s       | 0.03 s                                     |
| Build the template (migrate and read it)                         | 120 s       | 0.6 s                                      |
| Copy the template, first new database                            | 11.8 s      | 0.04 s native, 0.2 s with `pg_dump` replay |
| Campaigns subset, `-race`, warm template: time `go test` reports | 125 s       | 2.6 s                                      |
| Same, first run (CockroachDB builds its template, 240 s)         | 239 s       | 2.7 s                                      |

The compile of the `-race` binary is not in these times.
On CockroachDB the subset fails nothing.
On PostgreSQL one test fails: the TTL one, class (d).

The two PostgreSQL ways to copy the template:

| Variant                                  | Code                                                                                                   | Verdict                                                                                                                                                                                                                                |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Template and `DELETE`, as on CockroachDB | schema replayed from `pg_dump`, reference rows with `COPY`, `DELETE` to reuse                          | works; needs `pg_dump` on the runner                                                                                                                                                                                                   |
| `CREATE DATABASE … TEMPLATE` (default)   | one statement; copies reference rows too; retries error 55006 while another session is on the template | simpler, and about 5 times faster per copy. It would also let the kit drop `schemaDDL`, `routineDDL`, `orderByReferences` and `emptyAll` if databases are not reused. `MEURPG_TEST_PG_REUSE=0` drops each database at the end instead. |

## What CockroachDB gives that a move would lose

| CockroachDB                                       | PostgreSQL replacement                                                                                                           | Cost                                                                                                             |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Row-level TTL on 7 tables                         | Cloud Tasks sweep handlers with batch `DELETE` and indexes                                                                       | one handler and test per table; the code already has the sweep path                                              |
| Online schema changes that never lock a table     | `CREATE INDEX CONCURRENTLY`, `NOT VALID` constraints then `VALIDATE`, short `lock_timeout`; each migration reviewed for its lock | a rule in CONTRIBUTING and a lint for plain `CREATE INDEX` and `ADD COLUMN … DEFAULT` on big tables              |
| Built-in high availability and automatic failover | Cloud SQL regional HA, or a managed equivalent                                                                                   | a failover of about a minute rather than none; money                                                             |
| Serializable by default, 40001 retry at `RELEASE` | `default_transaction_isolation=serializable`, and `db/txpg.go`                                                                   | PostgreSQL aborts at `COMMIT` and has false positives; the retry loop must be the only way to open a transaction |
| `unique_rowid()`                                  | identity columns                                                                                                                 | one migration                                                                                                    |
| Horizontal scale                                  | a bigger instance, then read replicas                                                                                            | not a need at this size                                                                                          |

## Estimate of a real move

| Area        | Work                                                                                                                                            |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Schema      | Remove TTL from the migrations in a new migration; `STRING` to `TEXT`; `unique_rowid` to identity. Re-check every `CREATE INDEX`. About 2 days. |
| Retry       | Make `db/txpg.go` the only transaction path and test it under `-race`. About 1 day.                                                             |
| TTL         | 7 sweep handlers, their tests, and the class (d) tests. About 3 days.                                                                           |
| Data        | Dump and restore with a rehearsal on synthetic data (Phase 3), plus a cutover plan. About 4 days.                                               |
| Test kit    | Replace `schemaDDL` and friends with the native template; fix the lock-watching tests. About 2 days.                                            |
| Local setup | `make up`, `db-native-start` and CONTRIBUTING move to PostgreSQL. About 1 day.                                                                  |
| CI          | The `go-db` step is done here; the e2e and compose files need the same. About 1 day.                                                            |
| Docs        | ADR for the move, runbook, backup and failover. About 1 day.                                                                                    |

## Recommendation

Run the tests on PostgreSQL in development and in the CI of pull requests and trains.
Keep production, main and the nightly run on CockroachDB.

1. The class (b) finding stands on its own: on PostgreSQL the cockroach-go helper reports success for lost writes.
   Any transaction path that serves PostgreSQL must commit itself and read the `COMMIT` error.
2. The saving is large: a fresh migrate goes from 112 s to 0.5 s, and a template copy from 12 s to 0.04 s.
   In CI the slowest group falls from about 19 minutes to 11.
   The rest of the time is the `-race` build and the CPU-bound packages, which no database changes.
3. What the move would lose (TTL, online schema changes, built-in failover) matters in production, not in tests.
   That is why production stays on CockroachDB.
