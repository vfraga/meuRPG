# Design: the look of MeuRPG

MeuRPG looks like a **paper sheet** ("ficha de papel"): the official D&D 5e character sheet, with the same order and the same shapes (ability medallions, the AC shield, the proficiency dots), clean and readable on a screen, with a real light theme and a real dark theme.

This file is the reference for anyone who touches a screen in `web/`. The same system exists in Claude Design, with the components drawn, to design a new screen before the code:

- [MeuRPG — sistema visual](https://claude.ai/artifact/3wg7GmD4uuDEXhNP57ESdu) (Claude Design System);
- [MeuRPG — direções visuais](https://claude.ai/artifact/VDbSC4Y9H1z5vviHHL5nQm) (the three explored directions, each with a sheet and a campaign).

Both links are private until the project owner shares them.

**Language of the UI.** The UI text is Portuguese until i18n lands after the MVP, so this English file quotes UI strings in Portuguese ("Sair dos outros dispositivos"). The rules for that text are in [Text on screen](#text-on-screen).

## Principles

- **The game number comes first.** Modifiers, AC, HP and DC are the most visible things on the sheet. Everything else is quieter.
- **The sheet stays where the player is used to it** (MR-004): abilities on the left, then saving throws and skills, combat and spells in the middle, features and story on the right. On a phone, the same order in one column.
- **One bold move.** Burgundy appears once per screen as a fill (the main button) and otherwise as an outline (AC, HP) or text (links). No gradients, no decorative shadows, no card with a colored stripe on the side.
- **Structure is information.** A border, a panel and a divider separate things that really are different. Numbering only where there is a sequence (the editor's steps).
- **Both themes count the same.** Dark is for the evening session: every color has a pair in both themes, with AA contrast. The theme follows the operating system's.

## How a screen is made

Every new screen, and every visible change to a screen, goes through five steps:

1. **Brief:** the screen's single task, who uses it (master or player), where (phone at the table or laptop), the real data and every state (empty, loading, error, locked, pending, dead, no permission).
2. **Design in Claude Design,** with the system above, at 390px and 1280px, with real data. The project owner approves before the code. A small fix inside the system needs no design.
3. **Code with the tokens** below, never a hand-written color.
4. **Review on screen:** screenshots at 390, 768 and 1280px, light and dark, every state, checked against the design and the PR checklist (hierarchy, alignment, overlap, touch targets, focus, contrast, text). Look at each piece up close, in a 2x screenshot (buttons with an icon, fields, cards, notices): an icon 1px off the line of its words, or words glued to a border, do not show in a whole shrunken screenshot. The PR carries before and after screenshots.
5. **Automatic check:** `e2e/tests/a11y.spec.ts` runs axe and the alignment checks of `e2e/tests/layout.ts` on every screen and state it visits. Every new screen goes into it. The checks do not demand that everything be centered (the design decides); they catch what is never right: an icon off the height of its own words (more than 1px), a button's content off its middle, text on top of an icon, and words closer than 6px to the border of a radio card.

### Typography

Two OFL-licensed families, served by the app itself (packages `@fontsource/alegreya` and `@fontsource/alegreya-sans`, Latin subset only, which covers Portuguese). Never Google Fonts: the CSP (`font-src 'self'`) and [privacy](privacy.md) forbid asking a third party for a font.

| Style | Family | Size / line height / weight | Use |
| --- | --- | --- | --- |
| `display-xl` | Alegreya (`--mr-font-display`) | 48 / 48 / 800 | Character name (38 on a phone) |
| `display-l` | Alegreya | 38 / 40 / 800 | Page title, `.mr-page-title` (34 on a phone) |
| `title` | Alegreya | 21 / 26 / 700 | Panel title, `.mr-panel__title` |
| `stat-xl` | Alegreya | 40 / 40 / 800 | Max AC and HP |
| `stat` | Alegreya | 38 / 42 / 700 | Modifiers, initiative, speed |
| `body` | Alegreya Sans (`--mr-font-sans`) | 16 / 22 / 400 | Text and list rows |
| `field-value` | Alegreya Sans | 19 / 24 / 500 | Sheet header fields |
| `small` | Alegreya Sans | 14 / 19 / 400 | Supporting text |
| `label` | Alegreya Sans | 13 / 16 / 500 | Labels, `.mr-label`, never in capitals |
| `button` | Alegreya Sans | 16 / 20 / 700 | Buttons |

Numbers use `font-variant-numeric: lining-nums tabular-nums` (already in `body`), so the bonus columns line up.

Both families carry `ascent-override` and `descent-override` in `@font-face` (Alegreya Sans 92% and 28%, Alegreya 100.5% and 35.6%), which put the middle of the capitals at the middle of the line without changing its height. With the original metrics the letters sat above the middle, and every icon centered next to a text was 1 to 1.5px low ("← Básico", the notices, the back links). So an icon next to words takes no hand adjustment:

- on a single line, center both (`align-items: center`);
- when the text can wrap, align to the top and center the icon on the first line: `margin-top` = (line height − icon size) / 2.

**Checkboxes and radios.** The unchecked outline of every box and ring is `--mr-control-line`: Material's (`mat.checkbox-overrides` and `mat.radio-overrides` in `styles.scss`, `unselected-*-icon-color`), the drawn ones beside a hidden native input, and the native inputs that stay visible, which carry the class `mr-check-input` (`styles/_ui.scss`: `appearance: none`, a 2 px `control-line` outline, the accent when checked). The browser's own unchecked box is nearly invisible in the dark theme, so a visible native checkbox or radio always takes that class.

### Space and shape

- Spaces: `--mr-space-1` 4, `-2` 8, `-3` 12, `-4` 16, `-5` 20, `-6` 24, `-8` 48 (px). `--mr-gutter` is the side margin: 16 on a phone, 48 from 768px.
- Radii: `--mr-radius-sm` 8 (buttons, fields), `-md` 10 (notices), `-lg` 12 (panels), `-xl` 14 (medallions, header), `-pill` (tags).
- Borders, not shadows. The only shadows are an open dialog's and the edge of a `sheet-frame` that has more to scroll (10 px, at the top or the foot, only where there is more content), so a cut-off line is never a surprise.
- Layout: maximum width 1280px. The sheet has four columns on desktop, two on a tablet and one on a phone. Touch targets of at least 44px (48 on the main phone button).

Rules that hold on every screen:

- **A state tag is one word:** Rascunho, Pendente, Travada, Aprovado, Morto; invites Ativo, Usado, Expirado, Revogado. The notice beside it explains the rest ("Esperando a aprovação do mestre").
- **A pending item is not a reminder.** On the sheet, what the rules engine flags as a problem (armor without proficiency, a spell outside the spellbook) becomes a single notice right under the header, each item starting with the problem in bold. What is only a reminder (advantage against a spell, for example) stays, quiet, in "Características e traços".
- **An action that cannot be undone asks for confirmation on the screen itself:** "Marcar como morto" becomes "Confirmar morte", and "Recusar personagem" becomes "Confirmar recusa", with "Cancelar" beside it and focus on the new button.
- **A form in steps** (the sheet editor): each step is a tab, with the name in the header, and the content starts with "Passo N de M" and the title. On a phone the tabs become 44px numbers and the step title appears in the content. The save button sits below the open step, in any step; a step with an invalid field gets "(com erro)" on its tab, and submitting leads to the first of them.
- **One filled button per screen.** When a screen has two important actions (the master looking at a pending character), the main one ("Aprovar personagem") is the filled one and the other is outlined. The master's session page has none: its actions repeat per row ("Ajustar"), and the filled one sits where the decision is made, "Salvar ajuste". "Confirmar encerramento" uses an outline in the danger color, so it does not become the campaign page's second filled button.
- **Counts say "usados":** "1 de 3 usados", in spell slots, hit dice and the adjustment.

On the sheet: the ability medallion, the AC shield, the number boxes, the proficiency rows and the header fields, drawn in the Claude Design visual system.

Gallery rules:

- **Deleting an image that is a map's background** is refused by the server, and the card says which maps, through the `ImageInUse` detail: "Essa imagem é o fundo de Mirathel e arredores. Troque a imagem do mapa antes de apagá-la."

#### Joint turn

Combatants with the same initiative total play a single turn (MR-013, E8-01). The **"Turno conjunto" box** (`order-group`, a component of the combat screen, kept out of the initial bundle) is a 1.5 px `control-line` frame with 10 px corners, the word, the link icon and "iniciativa 19"; never a stripe on the side. The one whose turn it is gets the `accent-soft` background, the `accent` border and the "Vez" pill. Inside, each member has the state in word and icon (`part-state`: open circle and "Ainda age", or check and "Encerrou"). The **master's card** (`joint-card`) has one block per member, with the economy chips and "Encerrar a parte da Brisa" (outlined, 48 px on a phone and 44 px from tablet up, the block's width, only on whoever still acts); there is no "end the group's turn". **Distance always with squares (MR-013, E8-01).** Every distance the screen writes comes from `core/units.ts`, and displacement comes out in meters and in squares, "7,5 m · 5 quadrados" (1 square = 1.5 m = 5 ft; on the sheet, in feet, with "(25 pés)" at the end). The Movimento box says "7,5 m" and "5 quadrados livres"; a reach or the distance to a target stays in meters (`metersText`). "m" is never written by hand: the number and the unit travel together (non-breaking space) and the "·" never starts a line.

(`spell-help`) and the details sheet (`SpellDetails`) are a shared piece, of the sheet editor and of combat: `openSpellDetails` opens a sheet on a phone and a 560 px dialog from tablet up; over another sheet (the cast one), on a phone, it is a dialog drawn as a sheet, so the one below stays open. The title and "Fechar" stay in view and only the text scrolls. The SRD text stays in English. The body (`SpellBody`: the tags, the facts and the text) is a single piece, used by the dialog and by the "Magias" page card: the facts are in two columns in the dialog (the last, if the count is odd, takes the whole row: with "Alvo" there are five) and one per line, without boxes, in the page card; the "Alvo" line appears when the server says who the spell catches, and a table spell (`@mesa`) shows "Ataque" and "Dano" and the master's text, in Portuguese, without the SRD mark.

#### Map layers (`shared/map-layers`)

The language of everything drawn on a map (`MAP-LANGUAGE`). `MapLayersOverlay` draws over the image, on the squares that `core/maps/layers.ts` decoded from `GetMapLayers` (the same byte format as `rules/grid`; it is drawing, not rule): **Parede**, the dark diagonal hatch over a veil; **Terreno difícil**, the crossed hatch, lighter; **Cobertura**, a dotted square in the middle of the square, filled from the bottom up to halfway ("Meia cobertura") or to three quarters ("Três quartos"). The marks use the `--mr-map-*` tokens, which do not follow the theme, like the image. `MapLayersLegend` lists only the marks the map has, in this order, and the map screen projects its own (cards, reach, chosen square) into the same list; the swatches are `.mr-swatch` (`styles/_ui.scss`). Reading is `LayersState`: it reads the combat map again when `layers_revision` changes and keeps what is on screen if the read fails.

### Page title, "Pular para o conteúdo" and focus on navigation

Every page has its own title in the tab and in the history (WCAG 2.4.2), a first Tab that skips the bar (2.4.1) and takes focus to the new page's title on navigation (2.4.3).

- **Title:** `<page> · MeuRPG`, in Portuguese, only the first letter capitalized ("Minhas campanhas · MeuRPG"). Each route has its own in `title` (`web/src/app/app.routes.ts` and the `*.routes.ts` of the child routes); a new route without a `title` fails the `page-title.spec.ts` test. Where the page shows a campaign's or a character's name, the name goes in front when the page loads it: `Pensantus · Ficha · MeuRPG`. The page calls `setPageSubject(() => name)` in the constructor (`core/title/page-title.ts`). Until the name arrives, the title is the short one, never the previous page's; leaving the page removes the name.
- **"Pular para o conteúdo":** the app's first link (`app.html`), hidden until it receives focus (off-screen, not `display: none`, so Tab reaches it). It takes focus to `<main id="main" tabindex="-1">` without going through the router.
- **Focus on navigation:** after a navigation to **another page**, focus goes to the `h1` (or, without an `h1`, to `<main>`); the `h1` gets `tabindex="-1"` and, like every `[tabindex='-1']`, draws no ring (nobody tabbed to it). Focus does **not** move on the first load, on a change that only touches the query or the fragment (a filter), when the page already put focus on something inside it (dialogs and pages with their own focus) or while a dialog or sheet is open (`.cdk-overlay-container`).
- `a11y.spec.ts` checks all three, and `page-title.spec.ts` and `app.spec.ts` the edge cases.

The UI text is Portuguese (pt-BR) until i18n lands after the MVP; these rules are about that text, so the examples stay in Portuguese.
