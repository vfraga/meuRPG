## Fix direction for the confirmed findings

### U7-5, quadratic feature keys

- **Root cause:** `featureKeys` runs before any size bound, and `assign` rebuilds the taken-slug set per unkeyed feature.
- **Where:** `characters/tablecontent_rpc.go` `prepare`: count features (race/subrace traits, class levels' and subclass levels' features) and refuse above `MaxTableFeatures` with `invalid_argument` before `featureKeys`; then make `assign` incremental (keep one `taken` set, add each new slug, and remember the next suffix per stem so `uniqueSlug` is O(1)). The cheap guard alone fixes the exposure; the incremental set is the better second step. Pick both.
- **Same pattern elsewhere:** any other check that happens after a loop over client lists: `tablecontent.go:647` (`featureKeys`) is the one; also check `checkShape` callers and `UpdateTableEntry` (`tablecontent_rpc.go:441`). The 4 MiB body limit is `cmd/api/main.go:~124`.
- **Rules:** keep the 2,000-effect/500-formula/60-trait budgets and error shape (`invalid_argument` with the field path, `docs/architecture.md` "Error codes"); run `prepare` before the revision bump if possible, so a refused body does not hold the row lock.
- **Risk:** key stability: existing entries must keep their keys (keys never change); guard with the existing `tablecontent_*_test.go` key tests.

### U7-6, `dbError` inside transaction methods

- **Root cause:** `dbError` is meant for handler boundaries; inside a method that runs in the caller's transaction it replaces the pgx error with a fresh Connect error, which hides 40001 from `db.InTx`.
- **Where:** `characters`: give those methods the `wrap(...)` path when `tx != nil` (for example a helper `s.txError(ctx, tx, action, err)` that returns `wrap(action, err)` for a non-nil tx and `s.dbError` otherwise; `getVitals` keeps its deliberate `ErrNoRows -> errCharacterNotFound` mapping). `progression`: `requireMilestonesMode` and `sameRequest` called with a `tx`/`q` inside a closure should return `fmt.Errorf("...: %w", err)` and let the handler call `s.dbError` after `InTx`.
- **Same pattern elsewhere:** every `s.dbError` reachable with a non-nil tx: `characters/combatants.go:32,36,42,56,60,66,103,127,131,137`, `combatturn.go:39,46,50`, `vitals.go:226-238`, `combatmonsters.go:53,86`, `charactercreatures_roster.go:345,352`, `partyvision.go:27,31,43`, `mapcharacters.go:34`; `progression/milestones.go:394-397`, `award.go:432,441`. Grep `dbError(` in functions with a `tx pgx.Tx` parameter in `play` and `maps` implementations too.
- **Rules:** architecture "Transactions and the connection pool" (propagate with `%w`); only the pool path (`tx == nil`) may log and go on.
- **Risk:** error codes seen by clients stay the same after the retries are exhausted (`rpcerr.FromDB` at the handler); the `ErrNoRows` mapping inside `getVitals` must stay.
- **Sketch:** `if tx != nil { return wrap(action, err) }; return s.dbError(ctx, action, err)`.

### U7-4, preview leaks a switched-off choice

- **Root cause:** the archived/off check is guarded by `plan.refusal == nil`, but `PreviewLevelUp` treats only those two reasons as "build no sheet".
- **Where:** `characters/levelup.go` `planLevelUpIn`: compute the archived/off refusal first for a player (or keep a separate `plan.hiddenChoice` flag set whatever the earlier refusal) and have `PreviewLevelUp` drop `after` when the flag is set. Alternative: in `PreviewLevelUp` return no `after` whenever any refusal is set; simpler, but the screen then loses the preview for legitimate refusals. Pick the flag.
- **Same pattern elsewhere:** `GetLevelUpOptions` filters subclasses and spell lists for players (`levelup.go:~265-285`); check `ListSpells`/`GetSpellDetails` previews for the same "earlier error masks the filter" shape. `LevelUpCharacter` is safe (any refusal is an error).
- **Rules:** RN-23 (switched off = archived for players in every read); no new error code.
- **Risk:** the web preview screen; `TestRN23_APreviewOfARetiredChoiceCarriesNoSheet` guards the current behaviour.

### U7-8, create replay across users

- **Root cause:** the create key is global per campaign, not per principal, and the request hash does not include the caller.
- **Where:** `characters/rpc.go` `CreateCharacter`: scope the key with the user, as `notes/rpc.go` does (`idem.Scope(campaignID+userID, key)`), or put `m.UserID` in the hash and refuse a replay whose row is not the caller's with the usual `not_found`. Pick the scoped key: it also stops B's key from colliding at the unique index.
- **Same pattern elsewhere:** `GiveCreature` (`charactercreatures.go:289-302`) and table entries (`tablecontent_rpc.go:287`) are master-only and campaign-scoped, so another master of the same campaign is the only collision; scoping by user is harmless there too. Check `progression` keys (`GetXPAwardByKey` per campaign): master-only, same note.
- **Rules:** `docs/data.md` "Idempotency columns" (the unique index is on the stored key; changing the stored value is compatible with old rows only if old rows are never replayed with the new scoping, which holds because keys are per form).
- **Risk:** an old client retry after a deploy would create a second character only if the first row was stored unscoped; `idempotency_test.go` guards the replay behaviour.

### U7-1, undo does not restore a clamped award

- **Root cause:** the share records the requested amount, not what the sheet gained.
- **Where:** `characters.AddExperience` already returns before/after; `progression/award.go` should store `after - before` in `xp_award_shares.xp` (or add a column `applied_xp`) and `undo.go` should subtract that. Alternative: keep the nominal share and store the previous XP, then set it back on undo; that restores exactly but overwrites a later edit, so pick the applied-delta option.
- **Same pattern elsewhere:** `AwardXPResponse.xp_each` and the event payload `XPEach` are nominal too; the milestone path has no XP so it is unaffected; the treasure gold award uses the same shares.
- **Rules:** history is never rewritten (ADR-0007): do not change old rows; for old rows treat a missing `applied_xp` as the nominal share. Update `docs/data.md` "progression and notes modules" and the "Undo" bullet.
- **Risk:** `TestUndoTakesBackOnlyTheLastAward` and the `gold_test.go` undo tests; a migration must be re-runnable (`ADD COLUMN IF NOT EXISTS`).

### U7-7, familiar's eyes left on after dismissal

- **Root cause:** the sight state lives on the vitals row but is hidden by `liveFamiliar` when the familiar is gone, so the code that ends the sight cannot see it.
- **Where:** either `play` ends the sight in the same transaction as `DismissCreature`/a familiar reaching 0 HP, or `liveFamiliar` stops hiding a sight that still has `ConditionsGiven` (smaller). Pick the second.
- **Same pattern elsewhere:** Wild Shape on the sheet (`wildshape.go`) and `SyncCreatures` after a familiar dies: check the same hide-then-leak shape.
- **Rules:** if the documented limit ("for the master to remove") is kept, change nothing but fix the part that is not documented: the end of combat should clear the sight's conditions; update `architecture.md` ~1993 either way.
- **Risk:** `familiarsight` tests in `play`.

## Unverified: what would settle each

- U7-9: a test with a second connection that commits `MarkCharacterDead` (or a level-up) between the `Party` read and the transaction, or a unit test that injects a stale `Party`.
- U7-10: two real concurrent `StartEncounter` calls with a fresh monster key on a pool of at least 2 connections (`dbtest.PoolSize`), asserting both succeed.
- U7-11: a direct `GiveCreature` call twice without a key (expect two creatures), plus a two-connection interleaving with `StartEncounter`.
- U7-12: a load test of `UpdateTableEntry` with a few thousand NPCs; likely only a low-severity operational note.

## Checked and clean (no finding)

- Authz matrix and IDOR: every characters RPC checks the role first and every query filters by campaign; a player gets the same `not_found` for another player's character, an NPC or a missing id; the only candidate (U7-8) is about idempotency, not access.
- RN-01 lock: edits go through `mayEditSheet` under `FOR UPDATE`, before the revision check; level-up is owner-only and rebuilds from the stored sheet.
- RN-03: one living character per player and campaign by a partial unique index plus a clean error; a character cannot belong to two campaigns (it has one `campaign_id`).
- Level-up: serialised by the row lock and the revision check; a repeat or a second tab gets a stale revision; one level at a time (`rules.ApplyLevelUp`); the kept roll is the server's.
- Notes: all SQL filters by author; clues and scene labels travel only for discovered scenes; the 300-note cap runs count then insert in one transaction.
- Treasure conversion and milestones: row locks plus uniqueness make a treasure convert once; mark/undo/give-again lock the planned milestone.
- Table content: write RPCs master-only, archived/off entries filtered consistently for players (a player cannot re-read the entry text of an archived entry their own sheet uses through `ListTableEntries`, unlike `ListContent`; judged an intent question, not listed).
