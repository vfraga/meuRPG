# Review unit 9: the SQL, the migrations and the RN-10 safety net

- **Scope:** every `backend/internal/*/queries.sql` read as SQL (plus the Go callers), the 177 goose migrations, `backend/cmd/migrate` and the migration lock, `platform/dbtest`, and `internal/leaktest` (coverage gaps).
- **Commit reviewed:** `ae40f74` (`main` of the fork).
- **Time spent:** about 1 h 30 min of wall clock (six parallel read-only hunts, then three waves of independent verifiers).
- **Model:** the main session and the six hunting agents ran on Claude Sonnet 5.5 (`claude-sonnet-5-5`); every verification subagent was started with `model: sonnet` (Sonnet 5.5). Verifiers saw only the candidate's description, never the hunter's reasoning.
- **Method:** each confirmed finding has a failing test named `TestReview9_<Short>` next to the code, with a comment `// Finding U9-nn: ...`. No production code or migration was changed. The tests assert the *correct* behaviour, so they fail today.
- **Run all of them:** `export MEURPG_TEST_DATABASE_URL='postgresql://root@localhost:26257/defaultdb?sslmode=disable'; cd backend && go test -race -run 'TestReview9_' ./internal/campaigns/ ./internal/characters/ ./internal/maps/ ./internal/play/ ./internal/progression/ ./internal/leaktest/ ./migrations/` (the migrations package alone takes about 5 minutes).

## Answers to the unit's questions

- **IDOR in SQL (a `WHERE` without campaign, session or owner):** none found. Every player-serving query in campaigns, identity, notes, progression, characters, play and maps is scoped by campaign directly or through a prior `...InCampaign` lookup; id-only `UPDATE`/`DELETE`s only receive ids found earlier inside the locked session or encounter. The only cross-user hole is idempotency-key replay (U9-06, U9-07), which is not a `WHERE` problem but a replay without an owner check.
- **`:one` returning no row or several:** every `:one` is backed by a primary or unique key and its callers handle `ErrNoRows`. No finding.
- **Migrations on a second run:** a scripted audit of all `Up` sections plus a real double run (all migrations applied, rows inserted, `goose_db_version` cleared, `migrate up` again) found nothing; the `characters` TTL expression holds after 00122 and 00179 (the real TTL job deleted only the orphan row). No finding.
- **Migration lock:** correct on the paths checked (single atomic upsert on the database clock, own-row renew and release). Only low-severity caveats, left unverified (U9-28).
- **Leak tests:** the gaps are real (U9-15, U9-16, U9-17, U9-18); see the table.

## Fix directions (confirmed findings)

### U9-01, 40001 turned into Aborted inside `InTx`
- **Root cause:** `rpcerr.FromDB` returns `connect.NewError(code, errors.New(message))`, dropping the cause, so any `s.dbError(...)` returned from a closure hides the `*pgconn.PgError` that `crdb.ExecuteTx` looks for.
- **Where / approach:** (A, preferred) make the error built by `FromDB` keep the original error as its cause (a small wrapper type with `Unwrap() error`, or `connect.Error` constructed around a joined error whose `Unwrap` reaches the `PgError`), so every call site becomes retry-safe at once. (B) in each closure return `fmt.Errorf("...: %w", err)` and call `s.dbError` only on the value `InTx` returns. A is a one-file change and covers the pattern everywhere; B is explicit but must be repeated per call site and is easy to forget.
- **Same pattern elsewhere:** `progression/award.go:262,267,274,432,441` and `progression/milestones.go:397` return `s.dbError` from code that runs in a closure; audit every `dbError(`/`FromDB` call lexically inside a `db.InTx` or `db.ReadTx` closure in all modules (progression is confirmed, others not tested).
- **Rules to respect:** wrap with `%w` inside closures (`db.InTx` doc, architecture "Transactions and the connection pool"); client-facing message and code stay as in "Database errors"; no new dependency.
- **Risk:** `FromDB` is used everywhere, so a cause that is now visible must not leak into the client message or logs differently; existing `rpcerr` tests and the `TestRN09_...` progression tests guard it.
- **Sketch:** `return connect.NewError(code, &causedError{msg: message, cause: err})` with `func (e *causedError) Error() string { return e.msg }; func (e *causedError) Unwrap() error { return e.cause }`.

### U9-02, `CreateMap` closure not idempotent
- **Root cause:** the closure assigns to a variable captured from outside (`imageID`, line 301) that its own first step (`checkImage`, line 294) reads.
- **Where / approach:** use a closure-local `effectiveImageID := imageID` assigned at the top of each run and use that for the insert; keep `used` reset as it is.
- **Same pattern elsewhere:** audit closures that assign captured variables before reading them: `maps/mapservice.go` `UpdateMap`, `SetMapFog`, `UseGeneratedImageAsMapImage` (fog copy preparation outside the transaction, same `reuse`/`prepareReuseCopy` shape, line ~294-314) and `maps/imagegen.go` reserve.
- **Rules:** idempotent `InTx` closures; files are deleted only after a failed transaction, never inside it; `Gallery.PreparePortrait`/`Discard` flow in architecture.
- **Risk:** the fog copy gallery row is inserted inside the transaction, so a retry must insert it again; `maps` fog tests (`fog_round2_test.go`, `idempotency_test.go`) guard it. The new test forces the retry with a second connection inside `Config.Now`.

### U9-03, key reuse with a different award
- **Root cause:** `sameRequest` compares a hand-picked subset of fields instead of a hash of the whole request like other create RPCs.
- **Where / approach:** store and compare `idem.Hash` of the whole request (mode, amount/gold, sorted `character_ids`, `encounter_id`, reason, milestone fields) in `xp_awards` (new `create_hash` column via a new migration, idempotent, with `IF NOT EXISTS`), or at minimum compare amount, character set and encounter in `sameRequest`. The hash column matches `docs/data.md` "Idempotency columns" and rule 9; the field-compare fix needs no migration but drifts when fields are added.
- **Same pattern elsewhere:** `maps/imagegen.go:396,577,693` (U9-13) and the replay of `milestone_again` only; every table in the data.md idempotency table that lacks `create_hash` (`xp_awards`, `image_requests`, `session_events`, `puzzle_moves`, `puzzle_hint_tries`) should be checked.
- **Rules:** key reused for another change returns `invalid_argument` via `idem.ErrReused`; the undo has its own key; docs `data.md` "Idempotency columns" change.
- **Risk:** existing awards have no hash, so a missing hash must keep today's behaviour; `stories_test.go` and `xpmode_test.go` guard the flows.

### U9-04, undo after the XP clamp
- **Root cause:** the share records the requested XP, not the XP actually added.
- **Where / approach:** `characters.AddExperience` returns the real delta and `progression.give` stores it in the share (undo then subtracts exactly that), or reject awards that would pass the cap. Storing the delta keeps the cap behaviour; rejecting changes the player-visible rule.
- **Same pattern elsewhere:** the clamp at 0 for negative amounts (tested) and any other `AddExperience` caller (level-up reasons, milestones).
