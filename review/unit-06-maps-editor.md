## Fix directions

### U6-B: hidden NPC portrait reaches the model in a textured map
- **Root cause:** the hidden-portrait guard lives in `checkCharacters`, which `prepareMap` only calls for scene art and isometric; the textured branch assumed "no characters" meant "no way to pass a portrait", but `object_image_ids` still accepts any gallery image.
- **Where:** `imagegen_map.go` `prepareMap`/`checkCharacters`. Split the refusal into its own step that needs only `npcTokens` and the visible set (`playersSeenOf`) and run it for every map kind. Alternative: for the textured map refuse every NPC portrait that has a token on the map, seen or not (cheaper, no fog compile, slightly stricter). I would pick the alternative: the textured map starts from the whole map and carries no creature, so no NPC portrait has a reason to be in it.
- **Same pattern elsewhere:** `GenerateSceneImage` (no map, `imagegen.go:260`) and `EditGeneratedImage` (`:308`) pass `object_image_ids`/`character_image_ids` with no portrait check at all (a hidden NPC's portrait can be chosen as a plain scene reference; the doc says that is the master's choice when it is not tied to a map). An edit of a map picture (`imagegen.go:627-664`) re-sends the previous image only. `checkCharacters` also skips NPCs `MapCharacters` omits (dead or pending, `imagegen_map.go:304-308`).
- **Rules to respect:** RN-10 and RN-28, no read through the pool inside `InTx`, the check must stay before reserving the slot. Docs: "Images made from a map" ("The NPCs that appear", "The textured map") and `docs/privacy.md` "What generated images send to Google".
- **Risk:** a master loses the ability to use an NPC's portrait as an object reference in a textured map; `TestMR039_*` map tests and `imagegen_map_test.go` guard the refusals.

### U6-C: a paid picture that cannot be stored refunds the slot
- **Root cause:** `run` treats "the picture could not be stored" like "nothing was generated" and calls `finishFailed` (which sets `refunded`), although the call was made and may have been billed; the docs keep the slot spent for every other case after `sent_at`.
- **Where:** `imagegen.go` `run`, L1213-1249. Approach A: after a successful `Generate`, finish with a new query that sets `status=failed`, `reason` and keeps `refunded=false` (slot spent, no image). Approach B: make uploads (`upload.go:241`) and gallery copies count open image requests like `reserve` does, so storing never hits the quota. A fixes the cost, B fixes the cause for the gallery but not for decode failures or bytes. I would do A, and B for the count of images.
- **Same pattern elsewhere:** `finishFailed` after `Generate` returns an error (`imagegen.go:1195`: timeout, cut connection, unreadable response, `ErrNoImage`) also refunds although `gemini.go:138` says those calls "may have been billed"; the docs list them as returning the slot, so decide the policy once. `reserve` never reserves bytes (`imagegen.go:617`). `expireStale` keeps a lost sent request spent, the opposite policy.
- **Rules:** RN-28 (month tally), the daily cap in `docs/architecture.md` "Abuse limits", `FinishImageRequestDone` is allowed once; no new dependency. Docs to change: "AI-generated images" (Failures list) and `docs/operations.md` "Generated images".
- **Risk:** a master loses a slot when the gallery is full at the end; `TestMR039_RequestsInFlightCountAgainstTheGallery`, `TestMR039_TheLastSlotGoesToOneRequest` and the failure tests in `imagegen_test.go` guard the rest.

### U6-E: dungeon create checks the caps after rendering
- **Root cause:** the cheap checks (map count, gallery room) are inside the transaction, which runs after `drawDungeon` and the blob writes; the render also builds a reference JPEG that `putImageFiles` throws away (about 2.3 s of the 2.7 s on the largest map, per a measurement of `images.Encode`).
- **Where:** `dungeons.go` `CreateDungeonMap` (and `RedrawDungeon` at `:483`). Add a pre-check with `CountMaps` and `GetGalleryUsage` through the pool, before `drawDungeon` (the in-transaction check stays authoritative), and call `images.Encode` with `makeReference=false` for dungeon images. Alternative: take the limiter token only after the pre-check. Pick both.
- **Same pattern elsewhere:** `RedrawDungeon` (`dungeons.go:483`) pays the same render; the upload path decodes before the quota check (unit 5); `GenerateMapImage` is already ordered correctly (it checks the month before preparing).
- **Rules:** no read through the pool inside `InTx` (the pre-check is outside it), idempotency key lookup must still come first, `resource_exhausted` code. Docs: "Generated dungeon maps" and "Abuse limits".
- **Risk:** the pre-check can disagree with the transaction under races (only more refusals at the edge); `TestMR010_AFailedCreationLeavesNothingBehind` encodes the current order in a comment and must be updated.

### U6-A: "Usar" after an adjustment of a used picture
- **Root cause:** an edit inherits the source request's basis (`MapImageID` = the original map image), but after "Usar" the map's image is the source picture.
- **Where:** `reserve` (`imagegen.go:653-662`) or `UseGeneratedImageAsMapImage` (`imagegen_map.go:794`). Option 1: accept `locked.ImageID == source request's used_map_image_id` (the picture, or its fog copy, that "Usar" put on the map). Option 2: re-base the edit's basis to the map's current image when the source was used. Option 1 is smaller. Same size, grid and wall hash checks still apply.
- **Same pattern elsewhere:** none found; `docs/architecture.md` "Images made from a map" should say whether chained use is meant.
- **Risk:** the size, grid and `map_plan_hash` checks must stay; `TestMR039_UseAnEditOfATexturedMap` and `TestMR039_UseAfterAndRacingRedraw` guard them.

### U6-F: puzzle reveal names a point on a hidden map
- **Root cause:** the puzzle consequence is checked only for campaign membership of the point (`PuzzleCheckPoint`), and the player-facing sentence is built from the point's name without asking whether the players see that point.
- **Where:** `maps/puzzleseam.go` `PuzzleCheckPoint`/`PuzzleRevealPoint` and `play/puzzles_play.go` `solveLine`. Approach A: when the puzzle is configured, refuse a LIGHT target and warn (or refuse) when the target's map is not seen by the players. Approach B: at solve time return the name only if `playersSee(map)` and `everyoneSees(point)` after the reveal, else a generic line ("Algo apareceu no mapa."). B also covers a map hidden after configuration; pick B, plus the LIGHT refusal in A so the solving move cannot fail.
- **Same pattern elsewhere:** other puzzle consequences that name a thing (door opened, clue given) should be checked the same way; `PuzzleOpenDoor` opens locked and secret doors on purpose and returns squares only. `RevealSceneClue` and the trap events already carry ids only.
- **Rules:** RN-10; the seam takes the caller's `tx` and must not read through the pool inside `InTx`. Docs: "Puzzles (MR-038)" consequences.
- **Risk:** the line the master expects changes for hidden maps; the existing puzzle tests in `play` (`puzzles_*_test.go`) guard the normal text.
