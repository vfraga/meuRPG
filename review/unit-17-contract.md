# Unit 17: the client-server contract (`review/unit-17-contract`)

- **Scope:** the `.proto` files and their comments against the server code that fills each answer and event, and the web code that reads them. Services covered: identity, campaigns, campaign document, notes, progression, characters, rules, table content, maps, dungeons, gallery, imagegen, treasure, play (live stream, scene, traps, puzzles), combat, encounters.
- **Commit reviewed:** `ae40f74` (`main`).
- **Time spent:** about 1 hour 15 minutes, finders and verifiers running in parallel.
- **Models:** the session ran on `claude-sonnet-5-5`. The finder subagents and the verification subagents also used `sonnet`.
- **Method:** five finder subagents, one per service area, listed candidates. Each candidate was handed (description only) to a fresh verifier, which wrote a failing Vitest spec or refuted it. All proofs are web specs, run with `cd web && npx ng test --watch=false --include '<spec>'`. No production code was changed. Server-side facts in the table come from reading the code; no Go test was written or run.
- The fog player-revision candidate (U17-10) was shown with a spec that feeds `CombatState` the revisions the server produces. The exact numbers are illustrative: the server-side claim that the per-player count is lower than the global counter was established by reading the code, not by a Go integration test.

## Fix directions (confirmed findings)

### U17-10: fog player revision against the global counter
- **Root cause:** `revision` means two different things: the global counter for the master and non-fog players, and a visible-event count for fog players, yet `CombatState.apply` orders every copy by it.
- **Where / approach:**
  - (A) Server: `play/combat_fog.go` `visibleRevision`. Keep a monotonic per-player value, for example never return less than the last revision handed to that user, or add a fog epoch.
  - (B) Web: `combat-state.ts` `apply`. Skip the "older than current" check for a copy obtained after a revision-0 hint, and clear the stored revision on a fog change.
  - I would pick (B) plus (A) if cheap: (B) is local and also covers reconnects, while (A) keeps the contract honest. (A) alone changes what every fog read returns.
- **Same pattern elsewhere:** other places that compare `revision` for ordering: `pages/live-session/vitals.ts` (`applyVitals`, vitals revision is a single per-row counter, fine today but see U17-7), `live-session.ts:577-601` (hint handler uses `revision === 0 || > current`). Check any ordering on `Encounter.revision` in `core/combat/*`.
- **Rules to respect:** RN-10 (a fog player must not learn the global event count; do not "fix" by sending the global revision to players); the revision-0 hint design in `docs/architecture.md` "Per-player combat under fog" (~line 1915). That doc says the app never reads the revision, which is not what the code does, so it changes with the fix.
- **Risk:** stale-copy overwrite in the non-fog path. Guard tests: `combat-state` specs and `live-session.spec.ts`.

### U17-1: pact slots missing from the sheet
- **Root cause:** the sheet view-model was built from `spell_slots` only; `pact_magic` is a separate field by contract.
- **Where:** `character-sheet-source.live.ts` (map `derived.pactMagic`), `character-sheet.types.ts` (`FullSheetVm`), `combat-column` template (draw a "Magia de pacto" row next to `spellSlotRows`).
- **Same pattern elsewhere:** the level-up summary (`core/levelup/levelup-summary.ts:227`) already uses it. Check the live session party panel and the adjust-vitals sheet (they carry pact slots, `VitalsVm`), and `summon-sheet.ts` (`slot.pact`) for how pact is labelled.
- **Rules:** the sheet is read-only here; wording "espaços de pacto" in pt-BR like the level-up page. No server change.
- **Risk:** the combat column layout. Guards: `character-sheet-source.live.spec.ts`, `sheet-format.spec.ts`.

### U17-7: dismissed familiar keeps the player in familiar sight
- **Root cause:** the sight is cleared on read (`liveFamiliar`) without a state change, so the vitals revision does not move and every consumer that orders by revision ignores the cleared copy.
- **Where, two options:** (A) server: in `DismissCreature` (and `CreaturesLeaving`) call `endSight` for the owner in the same `db.InTx` so the revision bumps and vitals are published. (B) web: re-read the vitals snapshot on `creatures_changed` (`live-session.ts:568`). I would pick (A): it fixes every client and a reconnect, and (B) leaves the blinded/deafened conditions given at the start of the sight unresolved.
- **Same pattern elsewhere:** any read-time derivation that hides state without a revision bump: check `liveFamiliar` callers (`vitals.go`) and other "hide on read" filters in `characters/` (dismissed or removed creatures). Also confirm the blinded/deafened conditions given when the sight started are removed on dismissal (not traced).
- **Rules:** one connection inside `InTx`; the closure must be idempotent (40001 retries); publish after commit.
- **Risk:** combat joins that already call `endSight` (`combat.go:412,715`). Guard: the familiar-sight tests in `characters` and `play`.

### U17-2 and U17-5: refusals shown as "server unreachable"
- **Root cause:** `describeConnectError` falls back to the unavailable sentence for any code a screen did not list, so a business refusal (`failed_precondition`, `resource_exhausted`) reads as an outage.
- **Where:** (A) per call: add a `FailedPrecondition` branch to `mapErrorMessage` for delete (reading `MapBlocked` through `editorErrorMessage` with a 'delete' profile) and a `ResourceExhausted` branch to `showErrorMessage`. (B) general: make the fallback in `core/connect/connect-errors.ts` distinguish "network or unavailable" from "any other Connect code" and use a neutral "Não foi possível concluir a ação" for the latter. I would pick (A) for the wording plus (B) as the safety net.
- **Same pattern elsewhere:** every `*-errors.ts` that goes through `describeConnectError` without all of `failed_precondition`, `resource_exhausted` and `aborted`. Check `map-errors.ts`, `shown-image-panel.ts`, `notes-errors.ts` (resource_exhausted), `spells-errors.ts`, `bestiary-errors.ts`, `creature-errors.ts`, `treasure-errors.ts`, `dungeon-errors.ts`. Also hide or disable "Apagar mapa" when a combat runs or treasure is found/converted, as the point editor does.
- **Rules:** the error codes table in `docs/architecture.md` ("Error codes"); show the typed reason, never the message text.
- **Risk:** per-screen specs (`map-errors.spec.ts`, `connect-errors.spec.ts`); (B) changes the text of existing tests that expect the unavailable sentence.

### U17-3: fog tiles never retried
- **Root cause:** the `(error)` handler only settles the tile; nothing re-requests a throttled tile.
- **Where:** `shared/fog-map/fog-base.ts` `settle`: on error, schedule a retry (a few seconds, capped, with growing delay) by changing a per-tile retry token in the URL, and only count the tile as done on load. Alternative: have the server queue instead of rejecting (more server change, no).
- **Same pattern elsewhere:** other `<img>` loads from rate-limited or throttled endpoints (`/images/*`, map tiles outside the fog base): `shared/map-view`, `shared/portrait`, `shared/gallery-picker`.
- **Rules:** the per-user tile burst (60, then 10/s) must stay; retries must not turn into a storm (cap the number and honour `Retry-After` of 2 s / the 429 value, which an `<img>` cannot read, so use a fixed backoff).
- **Risk:** the progress badge, the 512 MiB render budget (more retries, more renders). Guard: `fog-map.spec.ts`.

### U17-6: master cannot give back resource uses
- **Root cause:** the web's vitals draft was built before `resources_used` and `wild_shape_hit_points_current` were added to the contract.
- **Where:** `adjust-vitals.types.ts` (`VitalsDraft`, `changeBetween`), `adjust-vitals.ts` (a row per `VitalsVm.resources` entry, a beast HP field when in Wild Shape), `live-session.types.ts` `VitalsChange`, `live-session-source.live.ts:266-279`.
- **Same pattern elsewhere:** any request field with no caller in `web/src`: run the same check over all request messages (a grep of the field names of each request in `web/src/gen` against `web/src/app`).
- **Rules:** master only (RN-10 does not apply, but a player must not be offered it); the stale-revision rule for vitals.
- **Risk:** the adjust sheet layout. Guards: `vitals.spec.ts`, `live-session.spec.ts`.

### U17-8: `targets_per_level` ignored
- **Root cause:** `targetRule` assumes +1 target per slot level, instead of using the value the server sends.
- **Where:** `core/combat/cast-flow.ts:206-207`: `extra = targetsPerLevel * max(slotLevel - spellLevel, 0)` (keep `extraTargetPerLevel` as a fallback of 1 when `targetsPerLevel` is 0).
- **Same pattern elsewhere:** `maxTargets` use in the target step, preview texts in `shared/spell-details`, and the table-spell editor which writes `per_slot_level`.
- **Rules:** the server stays the authority (`combat_spells.go:166`); keep both limits identical.
- **Risk:** low. Guard: `cast-flow.spec.ts`.

### U17-9: `turn_changed` leaves the old turn group
- **Root cause:** `applyTurn` patches three fields of a copy that holds derived turn state (`turnGroupIds`, per-member flags).
- **Where:** `combat-state.ts` `applyTurn`: clear `turnGroupIds` (the code already falls back to `currentCombatantId`) and the per-member turn flags, or reload after `turn_changed` as well. Clearing is not exact for a real joint turn until the reload lands; a reload from `onTurnChanged` is the exact fix.
- **Same pattern elsewhere:** `applyMove` and other partial patches in `combat-state.ts`; check each for derived fields.
- **Rules:** the turn state is server-owned; do not recompute joint-turn membership on the client.
- **Risk:** double reloads. Guards: `combat-state.spec.ts`, `joint-turn.spec.ts`, `live-session.spec.ts`.

### U17-4: unchanged note save
- **Root cause:** `save()` builds an empty change and sends it.
- **Where:** `note-editing.ts` `save()`: when the change object is empty, close the form without calling the server. Alternative: have the server treat an empty update as a no-op. I would pick the web guard: it matches the proto, which documents the empty update as invalid.
- **Same pattern elsewhere:** other update calls that build a partial change object: check `core/*/` clients for `update` helpers with the same spread pattern (character story, campaign document name, table rules).
- **Rules:** the `invalid_argument` table in `docs/architecture.md`.
- **Risk:** low. Guard: `note-editing.spec.ts`.
